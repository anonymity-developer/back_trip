# DB 확장 개발 진행 기록

기존 0~6단계 상세 계획을 실제 개발에서는 다음 3개 페이즈로 묶는다. 각 페이즈가 끝나면 테스트 결과와 직접 확인 절차를 기록하고 커밋한다.

| 페이즈 | 범위 | 상태 |
| --- | --- | --- |
| 1. DB·적재 기반 | 전체 DDL·반복 가능한 업그레이드·기준정보·원본 검증·변환 적재·DB 검증 | 완료 |
| 2. 애플리케이션 연계·검증 | DTO/DAO/Service·검색 화면·구군 동기화·기존 참조·통합 회귀 | 완료 |
| 3. 최종 산출물·사용 안내 | 전체 ERD·최종 DDL·시연 데이터·검증 기록·직접 테스트 안내 | 완료 |

## 결정 사항

- 2026-11-06 사용자 승인: 기존 ID·비어 있지 않은 값을 유지하고 덤프는 신규 추가·누락 정보 보충에 사용한다(Q3).
- 같은 날 사용자 승인: 원본 SQL은 유지하고 39번 유형명을 별도 초기 데이터에서 ‘음식점’으로 보정한다(Q4).
- 실제 설치 MySQL: 8.0.46. 기존 실행 DB는 변경하지 않고 별도 인스턴스에서 검증한다.
- 빌드는 설치된 STS 내 Java 25 JDK로 `--release 21`을 사용한다. 기본 PATH의 Java 8은 사용하지 않는다. 실행·검증한 JDK와 소스 대상 버전을 구분한다.

초기 분석 당시의 ‘구현 미착수’ 서술은 계획 수립 시점의 기록이다. 현재 구현 상태는 이 문서를 기준으로 확인한다.

## 페이즈 1 결과

- 신규 설치 DDL은 전체 12개 테이블과 관광지의 시도·유형·복합 구군 FK를 포함한다. 기존 DB용 업그레이드는 자체 기준정보 적재와 사전 코드 검사를 포함하며 반복 실행 가능하다.
- 원본 생성기는 원본 파일의 해시를 기록하고 DROP 없이 새로운 검증 스키마만 생성한다. 제공 구군 FK를 복합 관계로 보완했다.
- 별도 MySQL 8.0.46·127.0.0.1:13307에서 원본 50,915건, 기준정보 17/234/8건을 실제 적재했다. 기존 구조에 관광지 2건·회원·계획·방문지·사진을 준비한 후 업그레이드·병합했다.
- 기존 전용 관광지 1건을 유지해 통합 50,916건. 기존 id=42, content_id=2733967의 제목·주소·설명·사진·갱신 시각 및 계획·사진 참조를 보존했다.
- 업그레이드·병합 재실행에서 추가 0·보충 0, 중복·고아·좌표 오류 0. 별도 신규 설치도 12개 테이블을 확인했다. 잘못된 시도·구군 쌍은 FK가 거부했다.
- 최초 검증에서 발견한 MySQL 정규식 개행 문자셋 오류를 수정한 뒤 재검증했다. 실패한 적재의 DML은 롤백되었다. 원본 로드를 반복하면 첫 CREATE SCHEMA에서 중단되는 것도 확인했다.
- 직접 확인 방법: [로컬 테스트 1~4절](06-local-test.md). 현재 실행 중인 기존 DB에는 접속·변경하지 않았다.

다음 페이즈에서는 이 DB에 앱의 DTO·DAO·Service·검색 선택지·구군 동기화를 연결하고 HTTP·기존 기능을 검증한다.

## 페이즈 2 결과

- DTO·DAO에 nullable 구군 코드, 조회 선택지에 DB 기준정보, 관광지·부가 정보 Controller에 Service 경유를 반영했다. 읽기 전용 `findStored`는 부가 API 조회에서 설명 수집·DB 쓰기를 새로 유발하지 않는다.
- 동기화는 기준정보의 지역·유형·구군을 검증하고 미등록 코드는 저장 전에 중단한다. API에서 빈/0 구군은 NULL, 0·범위 밖·비정상 좌표는 위치 미상으로 처리한다. 기존 설명 및 빈 응답으로 지워질 수 있는 주소·사진·갱신 정보를 보존한다.
- `ENJOYTRIP_SYNC_ENABLED=false`로 정기·수동 관광지/뉴스 동기화를 함께 중지할 수 있다. 관리자 화면에 중지 상태를 표시하고 직접 동기화 요청도 503으로 거부한다.
- `setup-test.py`는 별도 `enjoytrip_test` DB·제한된 전용 계정·로컬 설정을 준비한다. `run-local.ps1 -EnvFile`로 기존 `.env`와 분리해 실행한다.
- 실제 MySQL 8.0.46에서 단위·대역·DAO 통합 테스트 **9건 통과**. 통합 테스트의 최초 환경 오류(기존 JDBC가 빈 비밀번호를 거부)를 전용 계정으로 해결하고 재검증했다. 기본 실행에서는 DB 테스트 1건을 의도적으로 생략한다.
- Tomcat 11.0.26·포트 18080·관광지 50,915건의 테스트 DB에서 HTTP 회귀 통과: 공개 페이지, 필터·20건 카드·10건 자동완성, 상세·사진, 가입·프로필·탈퇴, 계획 방문지·순서·비공개, 공지/공유글 권한, Hot Place 사진 생성·조회·삭제, CSRF, 동기화 중지. 자동 생성 회원·콘텐츠는 종료 시 정리했다.
- 실제 외부 API는 호출하지 않았다. 키 없는 날씨 503·저장된 기본 화면 유지까지 검증했다.
- 직접 확인 방법: [로컬 테스트 5절](06-local-test.md#5-앱회귀-테스트).

다음 페이즈에서는 전체 ERD·검증 결과·실행 화면을 최종 산출물로 정리하고, 설치·복구·시연 절차를 마무리한다.

## 페이즈 3 결과

- [DB 산출물](../../deliverables/db/README.md)에 전체 12개 테이블 ERD(SVG·Mermaid)·컬럼 정의표·최종 DDL·실제 화면 6장·검증 결과를 정리했다. DDL 사본은 실행 원본과 바이트 단위로 일치한다.
- 선택적 시연 SQL은 전용 DB에 공개 계획·관광지 2개·공지·공유글을 만들며 두 번 실행해도 같은 계획 id를 유지했다. Hot Place는 실제 파일 업로드로만 검증한다.
- 최종 HTTP 회귀에 공지·게시글·사진 수정, 관리자 비밀번호 초기화·재처리 거부·임시 비밀번호 변경 강제를 추가하고 통과했다. 전체 HTTP 스크립트의 기대 결과는 5개 PASS다.
- 시연 데이터가 포함된 테스트 DB를 백업해 새 DB로 복원했고 12개 테이블 건수·관광지 ID 매핑·계획 방문지 매핑이 일치했다. 운영 사진 파일을 포함한 복원은 검증하지 않았다.
- 로컬 검색 응답 각 5회와 지역/유형 EXPLAIN을 기록했다. [측정값·조건](../../deliverables/db/verification.md#검색-측정)을 함께 제공하며 운영 SLA로 해석하지 않는다.
- 최종 검토에서 기존 비어 있지 않은 주소·설명·사진 URL의 앞뒤 공백까지 보존하도록 적재 SQL을 보완하고 HEX 값으로 동일성을 검증했다. 반복 적재의 추가·보충은 다시 0이었다.
- 루트 README의 오래된 문서 링크·DB 설치·테스트 개수를 현재 구현에 맞췄다. [직접 테스트 안내](06-local-test.md)에 시연·백업·복원·종료 방법까지 정리했다.

현재 개발 페이즈 1~3은 완료했다. 다음 실제 적용 작업은 사용자 환경에서 직접 확인한 뒤 기존 DB 백업·업그레이드·WAR 전환, 키/승인을 이용한 실제 외부 연동, 반별 규칙에 따른 최종 제출이다. 이번에 실제 사용자 DB를 변경하거나 GitLab에 업로드하지 않았다.
